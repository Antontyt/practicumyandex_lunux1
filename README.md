# Восстановление исходного кода скрипта после удаления файла

Скрипт checker_script.sh проверяет, что целевой скрипт /opt/script.sh запущен
и пишет в свой лог /opt/my.log. Если файл целевого скрипта удалили, а процесс
продолжает работать, скрипт восстанавливает исходный код из памяти процесса.

## 1. Краткое описание

Файл в UNIX исчезает не в момент удаления. Он исчезает тогда, когда на него не
осталось ссылок в каталогах и его не держит открытым ни один процесс. Пока
скрипт выполняется, интерпретатор держит его файл открытым, поэтому исходный
код можно прочитать обратно:

    /proc/<PID>/fd/<N>  ->  /opt/script.sh (deleted)

Достаточно скопировать содержимое этого дескриптора в файл, и код восстановлен.

## 2. Почему это работает

### 2.1 Имя файла и сам файл это разные вещи

Данные файла хранятся в inode: владелец, права, размер, указатели на блоки
данных. Имя, которое видно в каталоге, это всего лишь ссылка на inode. Сама
связь между именем и inode записана в каталоге.

    имя в каталоге  ->  inode  ->  блоки данных на диске
    /opt/script.sh      152        ...

Команда rm вызывает системный вызов unlink(). Он удаляет запись в каталоге.
Сам inode и блоки данных при этом не трогаются. Ядро освобождает их только
тогда, когда на inode не осталось ссылок из каталогов и счётчик открытых
дескрипторов равен нулю.

### 2.2 Интерпретатор держит файл скрипта открытым

Когда запускается bash script.sh, интерпретатор открывает файл скрипта и читает
его по ходу выполнения. Файл остаётся открытым на всё время работы процесса.
Эта открытая ссылка и не даёт ядру освободить inode. В списке открытых файлов
процесса она выглядит так:

    lr-x------ 255 -> /opt/script.sh

Номер дескриптора у bash постоянный, 255. Права только на чтение, тип ссылки
символический. Привязываться к номеру в скрипте не нужно, дескриптор находится
поиском по цели ссылки.

### 2.3 Пометка (deleted)

После удаления ядро дописывает к цели ссылки пометку (deleted):

    lr-x------ 255 -> /opt/script.sh (deleted)

Это единственный признак того, что файл удалён, а данные ещё живы. Пометку
ставит ядро, своих маркеров создавать не надо. По ней функция восстановления и
находит нужный дескриптор.

### 2.4 Почему процесс не падает и продолжает писать в лог

Причин две. Первая: уже прочитанная часть кода находится в памяти процесса.
Вторая: ещё не прочитанная часть доступна через тот же открытый дескриптор,
файл открыт, его блоки данных на месте.

Лог /opt/my.log скрипт открывает заново на каждую запись, через >>. К удалению
исходного файла это отношения не имеет, запись идёт как обычно.

## 3. Как найти удалённый скрипт в системе

### 3.1 По дескрипторам конкретного процесса

    PID=$(pgrep -f "script.sh")
    ls -l /proc/$PID/fd/
    readlink /proc/$PID/fd/255

Первая команда даёт PID работающего процесса. Вторая показывает его открытые
файлы, среди них надо искать ссылку с пометкой (deleted). Третья печатает цель
ссылки в виде текста.

### 3.2 По всей системе, если PID неизвестен

    ls -l /proc/*/fd/ 2>/dev/null | grep "(deleted)"

Здесь перебираются все процессы и все их открытые файлы. Тот же обход
использует и функция восстановления.

### 3.3 Готовые инструменты

    lsof +L1
    lsof +L1 -p $PID

Параметр +L1 означает, что показываются файлы с числом ссылок меньше единицы,
то есть удалённые. Если lsof в системе есть, им удобно посмотреть глазами.
В скрипте используется readlink, потому что он есть везде.

## 4. Восстановление

### 4.1 Суть в одной команде

    cat /proc/$PID/fd/255 > /opt/script.sh

Всё остальное в функции это поиск нужного дескриптора и обработка ошибок.

### 4.2 Разбор по шагам

Перебор /proc/[0-9]*/fd/* обходит все процессы и все их открытые дескрипторы
за один цикл.

readlink -- "$FD_LINK" превращает ссылку в текст вида /opt/script.sh (deleted).

Сравнение с "$SCRIPT (deleted)" отбирает только нужный файл. Имя script.sh
встречается в системе не один раз, поэтому сравнение идёт по полному пути.
Подставить чужой код хуже, чем отказаться от восстановления.

cat -- "$FD_LINK" > "$SCRIPT" копирует содержимое на место удалённого файла.
Файла там сейчас нет, поэтому перезаписывать нечего и временная копия не нужна.

Проверка [ ! -s "$SCRIPT" ] нужна на случай обрыва чтения. Пустышка на месте
рабочего скрипта хуже, чем отсутствие файла.

chmod +x возвращает восстановленному файлу бит исполнения.

В конце функция возвращает 0 при успехе или 1 при неудаче. По этому коду
вызывающая часть решает, продолжать проверки или завершиться.

Отдельно стоит сказать про двойной дефис в readlink -- и cat --. Он защищает от
цели, начинающейся со знака минус.

Если шаблон /proc/[0-9]*/fd/* не раскроется, переменная цикла получит этот
текст буквально. Отдельная проверка на такой случай не нужна: readlink вернёт
пустую строку, а она не равна строке с пометкой (deleted).

## 5. Порядок действий

Проверка занимает два шага. Сначала в фоне запускается setup.sh, затем
копируется и запускается checker_script.sh, который выполняет весь тест.

    # Шаг 1. Подготовка стенда, запуск в фоне
    ./setup.sh &

setup.sh создаёт целевой скрипт /opt/script.sh с shebang #!/bin/bash, очищает
лог /opt/my.log и запускает целевой скрипт в фоне. Целевой скрипт пишет в лог
по строке в секунду.

    # Шаг 2. Копируем checker и запускаем
    cp checker_script.sh /tmp/
    chmod +x /tmp/checker_script.sh
    /tmp/checker_script.sh

В самом скрипте эти действия идут в таком порядке: проверка наличия файла,
проверка процесса, проверка записи в лог, вызов recover_deleted_script.

## 6. Ограничения

### 6.1 Восстановить можно только при живом процессе

Это главное ограничение. Дескриптор живёт ровно столько, сколько живёт процесс.
Как только процесс завершился или получил сигнал, дескриптор закрывается,
счётчик ссылок на inode становится нулевым, и ядро освобождает блоки данных.
После этого восстановить файл можно только из резервной копии. Порядок действий
поэтому критичен: сначала найти и восстановить, потом останавливать процесс.

### 6.2 Права доступа

Читать /proc/<PID>/fd/* можно только у своих процессов, либо от root. Для чужих
процессов readlink вернёт ошибку. В функции она глушится через 2>/dev/null, и
такой дескриптор пропускается.

### 6.3 Не любой интерпретатор и не любой способ запуска

Bash держит файл скрипта открытым на отдельном дескрипторе. Другие
интерпретаторы могут вести себя иначе: например, прочитать файл целиком и
закрыть его, тогда восстановление не сработает.

Если скрипт был запущен как sh script.sh или через source, смотреть надо
соответствующий процесс.

Скрипт, переданный через stdin (bash < script.sh), файла на диске не имеет
вовсе, восстанавливать нечего.

### 6.4 Файловая система

Механизм опирается на inode, поэтому работает на обычных файловых системах
UNIX. На сетевых файловых системах поведение может отличаться.

## 7. Итоги

Команда rm удаляет имя файла, а не его данные. Данные живут, пока на них есть
ссылка из открытого файла.

Проверять надо открытые дескрипторы, а не диск. Проверка test -f на удалённом
файле скажет, что файла нет, но о доступности данных это ничего не говорит.

Восстановление возможно, только пока процесс жив. Здесь важен порядок действий.

Сравнение пути должно быть точным. Ошибка здесь означает подстановку чужого
кода.

Восстановление создаёт новую копию файла. Работающий процесс продолжает
выполняться из удалённого файла, а на диске появляется независимая копия с тем
же содержимым и другим inode.
